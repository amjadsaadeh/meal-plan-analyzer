## Summary

Phase 2 implements the working Celery task and the REST API that wraps it. The foundation from Phase 1 is complete: `BackgroundJob` model exists with migration 0025, Celery app is wired into Django (`config/celery.py` + `config/__init__.py`), Redis is the broker (`CELERY_BROKER_URL`), and `SITE_BASE_URL` is available for WeasyPrint's worker context.

The task (`generate_pdf_task`) is a straightforward adaptation of the existing `meal_plan_pdf` view. The key difference is that the view uses `request.build_absolute_uri()` for `base_url` and returns an `HttpResponse`; the task must use `settings.SITE_BASE_URL` for `base_url` and save the PDF bytes to `BackgroundJob.result_file` via Django's `ContentFile`. The existing `django_url_fetcher` in `views.py` already resolves static/media URLs to local file paths and is suitable for reuse in the task.

The API is a DRF `ModelViewSet` registered on the router as `export-jobs`. `create()` is overridden to validate `meal_plan_id`, create the `BackgroundJob`, and fire `.delay()`. `retrieve()` works unchanged. A `@action(detail=True, methods=['get'], url_path='result')` serves the PDF with `FileResponse`. Authentication is inherited from the global DRF `DEFAULT_PERMISSION_CLASSES = [IsAuthenticated]` setting already in `config/settings.py`.

**Primary recommendation:** Implement `meals/tasks.py` with `@shared_task(bind=True, soft_time_limit=300, time_limit=360)`, use `BackgroundJob.objects.filter(pk=job_id).update(...)` for progress milestones, save the PDF via `job.result_file.save(filename, ContentFile(pdf_bytes))`, and register `ExportJobViewSet` on the DRF router.

### Pattern 1: Celery Task Structure (`meals/tasks.py`)

**What:** A bound `@shared_task` that wraps the existing PDF rendering pipeline, updating `BackgroundJob` progress at meaningful milestones and handling `SoftTimeLimitExceeded`.

**When to use:** Always for this task. `bind=True` is required to access the task instance for future retries if needed; `soft_time_limit` and `time_limit` are set at the decorator level so they are always enforced regardless of how the task is dispatched.

**Key design decision — progress updates via `.update()` not `.save()`:** Use `BackgroundJob.objects.filter(pk=job_id).update(status=..., progress=...)` rather than loading the instance and calling `.save()`. This avoids loading a stale instance and accidentally overwriting a concurrent update, and skips `auto_now` field overhead.

```python
# meals/tasks.py
# Source: Celery 5.x official docs + project codebase pattern
import os
import logging
from celery import shared_task
from celery.exceptions import SoftTimeLimitExceeded
from django.conf import settings
from django.core.files.base import ContentFile
from django.contrib.staticfiles import finders
from django.template.loader import render_to_string
import weasyprint

from meals.models import BackgroundJob

logger = logging.getLogger(__name__)


@shared_task(
    bind=True,
    soft_time_limit=300,   # raises SoftTimeLimitExceeded after 5 min
    time_limit=360,        # hard kill after 6 min
    name="meals.tasks.generate_pdf_task",
)
def generate_pdf_task(self, job_id: str, meal_plan_pk: int) -> None:
    """
    Generate a PDF for the given meal plan and save it to BackgroundJob.result_file.

    Progress milestones:
      25%  — meal plan context loaded
      60%  — WeasyPrint HTML object created
      90%  — PDF bytes written
     100%  — file saved, status = done
    """
    try:
        BackgroundJob.objects.filter(pk=job_id).update(
            status=BackgroundJob.Status.RUNNING,
            progress=0,
        )

        # --- Milestone 1: load context (25%) ---
        from meals.views import get_meal_plan_context, django_url_fetcher
        from meals.models import SiteSettings

        context = get_meal_plan_context(meal_plan_pk)
        site = SiteSettings.get()

        if site.logo:
            context["logo_path"] = f"file://{site.logo.path}"
        else:
            logo_disk_path = finders.find("meals/img/logo.png")
            if logo_disk_path:
                context["logo_path"] = f"file://{logo_disk_path}"

        if site.minilogo:
            context["minilogo_path"] = f"file://{site.minilogo.path}"
        else:
            logo_disk_path = finders.find("meals/img/logo.png")
            if logo_disk_path:
                context["minilogo_path"] = f"file://{logo_disk_path}"

        BackgroundJob.objects.filter(pk=job_id).update(progress=25)

        # --- Milestone 2: render HTML (60%) ---
        html_string = render_to_string("meals/mealplan_pdf.html.j2", context)
        html = weasyprint.HTML(
            string=html_string,
            base_url=settings.SITE_BASE_URL,
            url_fetcher=django_url_fetcher,
        )
        BackgroundJob.objects.filter(pk=job_id).update(progress=60)

        # --- Milestone 3: generate PDF bytes (90%) ---
        pdf_bytes = html.write_pdf()
        BackgroundJob.objects.filter(pk=job_id).update(progress=90)

        # --- Milestone 4: save file (100% + done) ---
        plan_name = context["plan"].name
        filename_base = "".join(c if ord(c) < 128 else "_" for c in plan_name)
        filename_base = filename_base.replace(" ", "-")
        filename = f"{filename_base}-{job_id[:8]}.pdf"

        job = BackgroundJob.objects.get(pk=job_id)
        job.result_file.save(filename, ContentFile(pdf_bytes), save=False)
        job.progress = 100
        job.status = BackgroundJob.Status.DONE
        job.save(update_fields=["result_file", "progress", "status", "updated_at"])

    except SoftTimeLimitExceeded:
        logger.warning("generate_pdf_task soft time limit exceeded for job %s", job_id)
        BackgroundJob.objects.filter(pk=job_id).update(
            status=BackgroundJob.Status.FAILED,
            error_message="Task timed out (soft time limit exceeded).",
        )
    except Exception as exc:
        logger.exception("generate_pdf_task failed for job %s", job_id)
        BackgroundJob.objects.filter(pk=job_id).update(
            status=BackgroundJob.Status.FAILED,
            error_message=str(exc)[:1000],
        )
        raise  # re-raise so Celery marks the task as FAILURE in its own state
```

**Note on `save(update_fields=...)` at the end:** The final save updates `result_file` (requires calling `FileField.save()` first to write the file), `progress`, `status`, and `updated_at`. We use `update_fields` to avoid accidentally overwriting other fields.

### Pattern 2: BackgroundJob Serializer

**What:** Two serializers — one for creation (accepts `meal_plan_id`, writes-only) and one for status polling (reads `id`, `status`, `progress`, `error_message`).

### Pattern 3: ExportJobViewSet

**What:** DRF `ViewSet` (not `ModelViewSet`) with explicit methods: `create`, `retrieve`, and a `result` action. Uses `ViewSet` rather than `ModelViewSet` because we never expose `list`, `update`, `delete` — a `ModelViewSet` would expose those unnecessarily.

```python
# meals/views.py — add below existing ViewSets
from rest_framework import viewsets, status
from rest_framework.decorators import action
from rest_framework.response import Response
from django.http import FileResponse, Http404
from .models import BackgroundJob
from .serializers import BackgroundJobCreateSerializer, BackgroundJobSerializer
from .tasks import generate_pdf_task


class ExportJobViewSet(viewsets.ViewSet):
    """
    POST /api/export-jobs/          — create job + dispatch task
    GET  /api/export-jobs/<id>/     — poll status
    GET  /api/export-jobs/<id>/result/ — download PDF when done
    """

    def create(self, request):
        serializer = BackgroundJobCreateSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        meal_plan_pk = serializer.validated_data["meal_plan_id"]

        job = BackgroundJob.objects.create(
            task_type="pdf_export",
            task_kwargs={"meal_plan_pk": meal_plan_pk},
        )
        generate_pdf_task.delay(str(job.pk), meal_plan_pk)

        return Response(
            BackgroundJobSerializer(job).data,
            status=status.HTTP_201_CREATED,
        )

    def retrieve(self, request, pk=None):
        try:
            job = BackgroundJob.objects.get(pk=pk)
        except (BackgroundJob.DoesNotExist, ValueError):
            raise Http404
        serializer = BackgroundJobSerializer(job)
        return Response(serializer.data)

    @action(detail=True, methods=["get"], url_path="result")
    def result(self, request, pk=None):
        try:
            job = BackgroundJob.objects.get(pk=pk)
        except (BackgroundJob.DoesNotExist, ValueError):
            raise Http404
        if job.status != BackgroundJob.Status.DONE or not job.result_file:
            raise Http404
        response = FileResponse(
            job.result_file.open("rb"),
            content_type="application/pdf",
            as_attachment=True,
            filename=os.path.basename(job.result_file.name),
        )
        return response
```

The existing `meal_plan_pdf` view uses `request.build_absolute_uri()` for `base_url`. In the Celery worker, there is no HTTP request. The correct replacement is `settings.SITE_BASE_URL`, which was added to `settings.py` in Phase 1 specifically for this purpose.

The existing `django_url_fetcher` function in `views.py` resolves static and media URLs to local file paths using `finders.find()` and `settings.STATIC_ROOT`/`settings.MEDIA_ROOT`. ### Pattern 6: Saving PDF Bytes to FileField via ContentFile

Django's `FileField` stores a file path; to save in-memory bytes, use `ContentFile`:

```python
# Source: https://docs.djangoproject.com/en/5.1/ref/files/file/
from django.core.files.base import ContentFile

pdf_bytes = html.write_pdf()  # returns bytes
job.result_file.save(
    "filename.pdf",              # stored filename
    ContentFile(pdf_bytes),      # wraps bytes as a file-like object
    save=False,                  # don't call job.save() yet
)
# Then call job.save(update_fields=[...]) explicitly
```

The file is written to `MEDIA_ROOT/exports/<filename>` (as configured by `upload_to="exports/"` on `BackgroundJob.result_file`).

### Pattern 7: Testing Strategy

The tests for Phase 2 are API integration tests following the existing `tests/api/` pattern. The Celery task is NOT tested via a live worker in these tests. Instead:

1. **API tests** (in `tests/api/test_export_jobs.py`): Mock `generate_pdf_task.delay` using `unittest.mock.patch` to prevent actual task dispatch. Test that `POST /api/export-jobs/` returns 201 with correct fields. Test that `GET /api/export-jobs/<id>/` returns correct status. Test that unauthenticated requests return 403.

2. **Task unit tests** (in `tests/test_export_task.py`): Call `generate_pdf_task(job_id, meal_plan_pk)` directly (not `.delay()`) with `@pytest.mark.django_db`. This bypasses Celery entirely and tests the actual task logic, including `SoftTimeLimitExceeded` handling (by patching `weasyprint.HTML`).

### Anti-Patterns to Avoid

- **Don't use `CELERY_TASK_ALWAYS_EAGER` in tests:** The Celery docs explicitly state this is not suitable for unit tests — it's an emulation with significant discrepancies. Mock `.delay()` in API tests; call the task function directly in task unit tests.
- **Don't use `self.update_state()` for progress tracking:** `self.update_state()` writes to the Celery result backend, which is `None` for this project. Use `BackgroundJob.objects.filter(pk=job_id).update(...)` instead.
- **Don't import `get_meal_plan_context` at module level in `tasks.py`:** Import it inside the task function to avoid circular imports at startup (`meals.tasks` would import from `meals.views` which imports from `meals.models` which is imported by Django before the app is fully loaded).
- **Don't use `get_object_or_404` in the task:** The task runs in a worker, not a Django view. `get_object_or_404` raises `Http404`, which makes no sense in a worker context. Use `BackgroundJob.objects.get(pk=job_id)` and let exceptions propagate to the except block.
- **Don't call `job.result_file.save(name, content, save=True)`** (the default `save=True`): This calls `job.save()` internally without `update_fields`, which may overwrite fields you don't intend to change. Use `save=False` and then call `job.save(update_fields=[...])` explicitly.
- **Don't register `ExportJobViewSet` as a `ModelViewSet`:** A `ModelViewSet` exposes all 5 CRUD actions. `ViewSet` is correct here — only `create`, `retrieve`, and `result` are needed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| In-memory bytes to FileField | Custom temp-file writer | `ContentFile(pdf_bytes)` + `field.save()` | Django handles MEDIA_ROOT path construction, storage backend, and cleanup |
| File download response | Manual `open()` + `HttpResponse` | `FileResponse(file.open("rb"), as_attachment=True)` | `FileResponse` is a `StreamingHttpResponse`; closes file handle automatically; handles chunked transfer for large files |
| SoftTimeLimitExceeded handling | Custom signal/thread timer | `@shared_task(soft_time_limit=N)` + `except SoftTimeLimitExceeded` | Celery sends `SIGALRM` to the worker; the `billiard` prefork pool raises the exception in the task coroutine; no custom timer needed |
| Progress persisting | Celery result backend | Direct `BackgroundJob.objects.filter(pk=...).update(progress=N)` | Result backend is `None` by design; direct ORM update is idempotent and avoids Django ORM overhead from loading full model instances |

## Common Pitfalls

### Pitfall 1: Circular Import in tasks.py

**What goes wrong:** `from meals.views import get_meal_plan_context, django_url_fetcher` at the top of `tasks.py` causes an `ImportError` or `AppRegistryNotReady` error when Celery starts.

**Why it happens:** `meals/views.py` imports from `meals/models.py` and `meals/serializers.py`. When Celery autodiscovers tasks, it imports `meals/tasks.py` early. If `tasks.py` imports from `views.py` at module level, this creates a circular dependency before the Django app registry is ready.

**How to avoid:** Place the `from meals.views import ...` import INSIDE the task function body, not at the module level.

**Warning signs:** `ImportError: cannot import name ...` or `django.core.exceptions.AppRegistryNotReady` in Celery worker startup logs.

### Pitfall 2: SoftTimeLimitExceeded Does Not Trigger `on_failure`

**What goes wrong:** If `SoftTimeLimitExceeded` is caught in a bare `except Exception` block without also having a specific `except SoftTimeLimitExceeded` handler first, the job status may be set to `failed` correctly, but the exception is re-raised and Celery will mark the task as `FAILURE` in its own state — which is fine since `CELERY_RESULT_BACKEND = None`. The risk is catching it as a generic exception and logging a misleading error message.

**How to avoid:** Always catch `SoftTimeLimitExceeded` first (before `except Exception`), log it at WARNING level (not ERROR), and set a clear `error_message`. Then the `except Exception` catch-all handles other failures.

**Warning signs:** "Task timed out" appearing in logs as an unexpected error rather than a known timeout.

### Pitfall 3: FileResponse Leaves File Handle Open

**What goes wrong:** If `job.result_file.open("rb")` is called in a bare `open()` and the `FileResponse` is not used as the final return value, the file descriptor leaks.

**Why it happens:** `FileResponse` is a `StreamingHttpResponse` — Django closes the file after streaming. But if you call `open()` and then raise an exception before returning, the handle leaks.

**How to avoid:** The `FileResponse` constructor accepts the opened file object; Django handles closing it after streaming. No explicit `with` block needed. Check `job.status == DONE` before opening — this is the early-return 404 path.

**Warning signs:** File descriptor exhaustion under load.

### Pitfall 4: UUID PK Raises ValueError on Bad Input

**What goes wrong:** `BackgroundJob.objects.get(pk=pk)` raises `ValueError` if `pk` is not a valid UUID string (e.g., if someone passes `pk=abc` in the URL).

**Why it happens:** Django tries to coerce the string to a UUID before querying. If it's not a valid UUID format, Python raises `ValueError` before the query runs.

**How to avoid:** Catch both `BackgroundJob.DoesNotExist` and `ValueError` in `retrieve` and `result` actions, and raise `Http404` for both. Pattern: `except (BackgroundJob.DoesNotExist, ValueError): raise Http404`.

**Warning signs:** 500 errors for URLs like `/api/export-jobs/not-a-uuid/`.

### Pitfall 5: `get_meal_plan_context` uses `get_object_or_404`

**What goes wrong:** `get_meal_plan_context(pk)` calls `get_object_or_404(MealPlan, pk=pk)`. In the worker context, if the meal plan doesn't exist, this raises `Http404` (a subclass of `Exception`). The `except Exception` block will catch it, set `error_message=str(exc)` which is not particularly helpful, and mark the job as `failed`.

**Why it happens:** The function was designed for HTTP views. `Http404` in a Celery worker is harmless (it's caught), but the error message is generic.

**How to avoid:** This is acceptable behavior — the job will fail with a message. The API endpoint (`create()`) already validates that the `meal_plan_id` exists before creating the job (`BackgroundJobCreateSerializer.validate_meal_plan_id`), so this scenario only occurs if the plan is deleted between job creation and task execution. No code change needed; document it.

### Pitfall 6: `update_fields` Must Include `updated_at` for `auto_now` to Trigger

**What goes wrong:** When calling `job.save(update_fields=["result_file", "progress", "status"])`, the `updated_at = models.DateTimeField(auto_now=True)` field is NOT automatically updated unless it is explicitly included in `update_fields`.

**Why it happens:** Django's `auto_now` behavior with `update_fields`: if `update_fields` is provided, `auto_now` fields are only updated if they appear in `update_fields`. See [Django docs](https://docs.djangoproject.com/en/5.1/ref/models/fields/#django.db.models.DateField.auto_now).

**How to avoid:** Always include `"updated_at"` in `update_fields` when using it. Or use `.filter(pk=...).update(...)` for the progress milestones (which bypasses `auto_now` entirely — but for the final save this is fine since we set `updated_at` explicitly).

**Warning signs:** `updated_at` timestamp is stale even after the job completes.

## Open Questions

1. **`expires_at` — when to set it?**
   - What we know: The `BackgroundJob.expires_at` field exists (null by default). The cleanup mechanism is deferred to Phase 3/later.
   - What's unclear: Should the task or the ViewSet's `create()` set `expires_at` at job creation time?
   - Recommendation: Set `expires_at = timezone.now() + timedelta(hours=24)` in `ExportJobViewSet.create()` at job creation time. This satisfies the schema intent even before the cleanup mechanism exists. The exact TTL value can be configurable later.

2. **`max_tasks_per_child` — confirm it applies without Docker Compose running**
   - What we know: `CELERY_WORKER_MAX_TASKS_PER_CHILD = 50` is set in `settings.py` and applies to the local dev worker.
   - What's unclear: Phase 2 tests run without a real worker; this setting is verified only when a real worker is started.
   - Recommendation: Document a manual verification step: start `uv run celery -A config worker --loglevel=info` and run the task a few times, then confirm the worker restarts child processes. This is a Phase 2 or Phase 3 checklist item, not a blocker.

3. **Location of `django_url_fetcher` — views.py vs shared module**
   - What we know: `django_url_fetcher` currently lives in `meals/views.py`. The task must also use it.
   - What's unclear: Importing from `views.py` in `tasks.py` (inside the function) works but is architecturally odd.
   - Recommendation: Keep the import inside the task function body (per Pitfall 1 advice). This is acceptable in Phase 2. If it creates maintenance issues, move `django_url_fetcher` to a `meals/pdf_utils.py` module in a future refactor. Don't refactor it in this phase.
